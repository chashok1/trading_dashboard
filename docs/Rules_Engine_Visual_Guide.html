Rules Engine & Data-Flow Visual Guide

Trading Dashboard · generated 2026-05-21 · companion to docs/Screen_and_DataFlow_Reference.md

This guide answers three things: how the rules engine scores a signal, how data moves from an Excel feed to a recommended action, and what each screen is for. It is built from a read of etl/derive.py, etl/derive_actionable.py, etl/position_rules.py, etl/rule_groups.py, etl/compute_outcomes.py, and the API routers.

1. The rules engine — four layers

You author rules in three reference tables. The engine evaluates them once per symbol per day inside etl/derive.py::_derive_stks_impl, working bottom-up: atomic rules feed composite rules, composites feed rule groups, and the results land in drv_stks as JSONB. derive_actionable then resolves a single recommended action per symbol.

Atomic rules

An atomic rule (ref_trig_atomic_rule) is a single condition. It reads one indicator column, and eval_atomic_rule() turns the measured value into a weight. Each rule has a breakout band (brkeout_from/brkeout_to) and three weights (wt_below, wt_between, wt_above). The scoring_mode decides the shape: jump gives a hard step between the three weights, linear interpolates across the band, and sigmoid gives a smooth S-curve using score_params (k, x0).

Composite rules

A composite rule (ref_trig_composite_mapping) sums a list of members. A member is one of three kinds: an atomic member reuses an already-scored atomic; a data member is an inline atomic-style rule against any drv_cat/drv_ma column; a composite member is a nested composite. Nested composites are topologically sorted so children are scored before parents, and cycles are detected and broken. Each composite can carry a precondition_expr — a safe mini-expression such as is_held and last_price > 5 that, when false, skips the rule (it fails open on a parse error). A composite is considered fired when any member contributed a non-zero weight, not when the net score is non-zero — so a rule with offsetting +1 / −1 members still counts as fired.

Rule groups

A rule group (ref_trig_rule_group + ref_trig_group_member) is boolean logic — AND / OR — over composites and nested groups. AND chains short-circuit; any OR member makes the group an any-true test. A group with group_type='action' carries an action_label (REMOVE / REDUCE / INCREASE / ADD / HOLD) and a numeric priority where lower wins; group_type='logical' groups exist only to be nested inside action groups.

From scores to a recommended action

The engine writes drv_stks with three JSONB columns — triggered_atomic_ids, triggered_composite_ids, triggered_group_ids. A parallel table, drv_trig, records a per-(symbol, composite) score and is what the Trace screen reads. derive_actionable is the resolver: it puts the rule-group actions into one pool with the per-source outlook actions, picks the most-aggressive action by ACTION_RANK (REMOVE 4 → HOLD 0), breaks ties by priority, resolves a sizing category through ref_asset_allocation, computes a suggested dollar target, and applies position-aware suppression — REMOVE on a position you don't hold, ADD on one already established, INCREASE at the ceiling, REDUCE at the floor. The suppressed action is preserved with a reason so you can still see what the engine wanted to do.

2. End-to-end data flow

Data moves in one direction with a feedback return. Seventeen Excel feeds load into 17 raw hist_* tables, every load triggers the derive cascade, the rules engine and resolver produce actions, the screens read them, and logged decisions feed back to tune the rules.

Raw data is sacred: all hist_* inserts use ON CONFLICT DO NOTHING and nothing but etl/cleanup.py ever deletes. Every load runs derive_all(D) in-process, which rebuilds the derived tables in dependency order. The cascade is, in order: drv_td, drv_tw, drv_sss, drv_cat_atomic_input and the drv_cat_* tables, drv_quote, drv_ma, drv_dash, drv_stks, drv_cs_realized_gain, drv_dash_summary, drv_outlook_action, drv_actionable, drv_missing_symbols, drv_trig. Every step is idempotent — it deletes the rows for date D and re-inserts — so re-running is always safe, and a file landing on an old date forward-re-derives the later dates it invalidated.

The most common gotcha. Editing a rule on the Rules screen only changes the ref_trig_* definition tables. Nothing on the dashboards changes until a re-derive runs — either the next ETL load or a manual python -m etl.rebuild_rules. Until then every other screen still reflects the old rules.

3. The screen workflow

The rules-engine screens form one cycle. You author rules, a re-derive publishes them, you act on the results, performance data lets you measure, and that sends you back to authoring. Trace sits in the middle as the inspector you can open from anywhere.

4. Screen-by-screen reference

The app serves 16 screens. They fall into four roles: Decide screens where you make calls, Author screens that write rule definitions, Observe screens that read back what the engine did, and Ops screens for the data pipeline itself.
